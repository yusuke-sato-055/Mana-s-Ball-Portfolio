# クエスト・敵・ログ管理 移植用 Codex 実装仕様書

## 0. 目的

本書は、別ゲームへ以下の開発・運用管理機能を実装するための仕様である。

1. クエストを一覧、作成、複製、編集、検証、公開、無効化する。
2. 敵マスターと敵グループを一覧、作成、編集、検証する。
3. クエストからフィールド、試合ルール、敵グループへの参照関係を確認する。
4. 実行ログ、エラーログ、戦闘イベント、試合集計、管理変更履歴を検索・閲覧する。
5. 管理データを安全に実ゲームへ反映し、壊れたデータで試合を開始させない。

本書でいう「管理画面」はプレイヤー向け画面ではない。開発者または運用担当者向けの画面、エディター、デバッグツール、CLIのいずれかとして実装する。

以下の仕様書と組み合わせる。

- `docs/クエスト選択_敵戦闘パターン_移植用Codex実装仕様書.md`
- `docs/編成画面_移植用Codex実装仕様書.md`

## 1. Mana's Ball の参考実装

Mana's Ball には独立したCRUD管理画面はない。CSVを正としてロード・検証し、ゲーム内画面とレポートで確認する構成である。移植時は次を参考にし、管理機能を追加する。

| 目的 | 参照先 |
|---|---|
| クエスト・試合条件のロードと検証 | `manaball/battle_setup.py` |
| 敵・敵グループ・AIのロードと変換 | `manaball/data.py` |
| 戦闘ルールと確定イベント | `manaball/core.py` |
| クエスト選択・全ログUI | `manaball/ui.py` |
| 戦闘イベント収集とMarkdownレポート | `manaball/reporting.py` |
| 自由試合設定の原子的保存 | `manaball/debug_save.py` |
| クエストデータ | `data/csv/quests.csv` |
| 敵データ | `data/csv/enemies.csv`, `data/csv/enemy_groups.csv` |
| AIデータ | `data/csv/ai_profiles.csv` |
| 試合条件 | `data/csv/match_rules.csv` |

現行ログの重要な考え方:

- 判定は戦闘ロジックで一度だけ実行する。
- UIとログは確定済み結果を参照し、乱数判定やダメージを再計算しない。
- 試合中ログはメモリ上へ時系列収集する。
- 通常プレイだけ `log/play/`、CIだけ `log/ci/` へ保存し、テストはファイル保存しない。
- 保存失敗を試合結果へ伝播させない。
- レポートは一時ファイルへ書いてから最終パスへ置換する。

## 2. 管理機能の画面構成

```text
管理ホーム
  ├─ クエスト管理
  │    ├─ クエスト一覧
  │    └─ クエスト編集・検証・プレビュー
  ├─ 敵管理
  │    ├─ 敵マスター一覧/編集
  │    └─ 敵グループ一覧/編集
  ├─ 関連データ管理
  │    ├─ 試合ルール
  │    ├─ フィールド
  │    ├─ AIプロフィール
  │    └─ スキル参照（原則読み取り専用）
  ├─ データ検証
  │    └─ 全体検証結果
  └─ ログ管理
       ├─ 実行・エラーログ
       ├─ 試合一覧
       ├─ 試合詳細/イベント
       ├─ 集計レポート
       └─ 管理変更履歴
```

小規模なローカルゲームでは、上記を一画面のタブUIまたは外部エディターとして実装してよい。Web管理画面にする場合は認証と権限管理を必須とする。

## 3. 共通データ管理方式

### 3.1 状態

管理対象データは次の状態を持つことを推奨する。

```text
draft       下書き。ゲーム本番では使用しない
published   公開済み。プレイヤー向けロード対象
disabled    無効。IDと履歴は残すが新規利用しない
archived    保管。通常一覧から隠す
```

既存CSVの `enabled` だけを使う場合は、`published = enabled=true`、`disabled = enabled=false` と簡略化してよい。

### 3.2 ID規則

- IDは作成後に原則変更不可。
- 表示名は変更可能。
- IDは英数字、ハイフン、アンダースコア等、移植先の安全な文字だけを許可する。
- 大文字小文字の区別を仕様として固定する。推奨は小文字へ正規化。
- 削除したIDを別用途で再利用しない。
- 同一種類内で一意制約を持つ。

### 3.3 保存単位

推奨する保存API:

```text
list(type, filters, sort, page)
get(type, id)
createDraft(type, payload)
updateDraft(type, id, expectedVersion, patch)
validate(type, id)
publish(type, id, expectedVersion)
disable(type, id, expectedVersion)
duplicate(type, sourceId, newId)
export(type or all)
importDraft(payload, mode)
```

`expectedVersion` または更新日時を使い、別画面の更新を気付かず上書きしない楽観ロックを行う。

### 3.4 下書きと公開

編集フォームの入力を即座に公開データへ書き込まない。

```text
編集開始
  → 下書き保存
  → 単体検証
  → 参照先を含む統合検証
  → プレビュー/テスト戦闘
  → 公開
```

CSVファイルを直接編集するローカル構成でも、保存前の一時モデルへ読み込み、全検証成功後に原子的置換する。

### 3.5 削除

- 公開済みデータは物理削除せず無効化を基本とする。
- 他データから参照されている項目は削除・無効化前に参照元を表示する。
- 参照中の項目を無効化すると公開クエストが壊れる場合は拒否する。
- 下書きで一度も公開されていないデータだけ、確認後の物理削除を許可してよい。

## 4. クエスト管理

### 4.1 一覧画面

列:

- 状態。
- 表示順。
- クエストID。
- クエスト名。
- ルール種別。
- フィールド。
- 試合ルール。
- 敵グループ。
- 出場人数。
- 推奨レベル/コスト。
- 最終更新日時。
- 最終更新者。複数ユーザー運用時のみ。
- 検証状態。

機能:

- ID・名前の部分一致検索。
- 状態、ルール、フィールド、敵グループで絞り込み。
- 表示順、ID、更新日時で並び替え。
- 新規作成、複製、編集、プレビュー、無効化。
- 選択行から依存関係と直近試合ログを開く。

### 4.2 編集項目

`QuestDefinition` の項目は前仕様書に従い、少なくとも以下を編集可能にする。

- ID。新規作成時のみ。
- 名前、説明。
- 表示順、状態。
- フィールドID。
- 試合ルールID。
- 敵グループID。
- クリア条件、失敗条件。
- ルール種別。
- 初期オブジェクト保持者。
- 儀式等の必要保持ターン。
- 推奨レベル、推奨コスト。
- BGM上書き。
- 解放条件、報酬。移植先に存在する場合。

参照IDは自由入力より、検証済み候補を選ぶセレクトUIを優先する。ID直接入力を許可する場合は入力中に存在確認を行う。

### 4.3 即時表示する派生値

- 味方対敵の出場人数。
- 味方・敵の控え最大数。
- コスト上限。
- 勝利条件の自然文。
- フィールドサイズ。
- 初期配置数と不足数。
- 敵グループ人数。
- 敵の出場/控え一覧。
- 総敵能力または推定難度。

### 4.4 検証

必須エラー:

- 必須IDまたは名前が空。
- ID重複。
- 参照フィールド、試合ルール、敵グループが存在しないか無効。
- 未対応のルール種別。
- 出場人数がパーティー上限を超える。
- 敵グループ人数が敵出場人数未満。
- 敵グループ人数が敵パーティー上限を超える。
- 初期配置が人数分ない、範囲外、重複している。
- 初期保持者が該当ルールの有効な出場枠を指していない。
- 儀式維持で必要保持ターンが1未満。
- 上限値・倍率・推奨値が許容範囲外。

警告:

- 説明、推奨値、BGMが未設定。
- コスト上限0。
- 同じ敵グループ・フィールド・ルールのクエストが既に存在する。
- 推定難度と推奨値が大きく乖離する。
- 控えがいるが交代機能が無効。

エラーが1件でもあれば公開不可。警告は確認後に公開可能。

### 4.5 プレビューとテスト

- プレイヤー向けクエスト詳細のプレビュー。
- 編成画面へ下書きクエストを一時投入するプレビュー。
- 固定シードで戦闘開始する。
- AI対AIで1試合完走する。
- 複数シードのバッチ試合を実行する。
- 勝率、平均ターン、得点、戦闘不能、主要行動を表示する。

プレビュー実行は公開データやプレイヤー進行へ結果を保存しない。ログには `environment=preview` または `execution_mode=editor_preview` を付ける。

## 5. 敵マスター管理

### 5.1 一覧画面

列:

- 状態。
- 敵ID、名前、タイプ。
- 画像サムネイル。
- HP、リソース、主要能力。
- コストまたは危険度。
- 標準AI、AIレベル。
- スキル数。
- 使用中の敵グループ数。
- 最終更新日時、検証状態。

検索・絞り込み:

- ID・名前。
- 敵タイプ。
- AIプロフィール。
- 能力値範囲。
- スキル。
- 使用中/未使用。
- 公開/下書き/無効。

### 5.2 編集画面

- 敵ID。新規作成時のみ。
- 名前、タイプ、説明、画像。
- 最大HP、最大リソース。
- 主要能力値。
- 移動力等、移植先の共通戦闘能力。
- 順序付きスキルスロット。
- 標準AIプロフィール、AIレベル。
- タグ。例: 前衛、守備、奪取、得点、回復、ボス。
- 状態。

能力編集では最小・最大、合計値、既存敵平均との差を表示する。画像欠損は警告とし、文字フォールバックがある場合は公開可能。

### 5.3 スキル編集

- 候補は有効なスキルだけ。
- スキルID、名前、コスト、射程、用途タグを表示する。
- 同一スキルの重複可否をゲームルールに従って検証する。
- 装備枠区分がある場合は枠に適合する候補だけを出す。
- 無効化予定スキルを装備している敵を逆参照できるようにする。

### 5.4 検証

- 必須ID、名前、タイプ。
- 能力値とAIレベルが範囲内。
- 全スキルIDが存在し、有効で、装備規則に適合する。
- AIプロフィールが存在し有効。
- 画像ファイルの形式とパス。画像を必須にしない場合は警告。
- 敵タイプと能力・スキルの矛盾は必要に応じて警告。

### 5.5 複製

敵の追加は複製を主要導線にする。

```text
duplicateEnemy(sourceId, newId):
  copy editable master fields
  clear runtime-only fields
  set state=draft
  append "のコピー" to display name or request new name
  validate new ID uniqueness
  write audit event
```

## 6. 敵グループ管理

### 6.1 一覧

- グループID、名前、状態。
- 参加人数、想定出場人数。
- 敵の簡易アイコン列。
- 共通AI、能力倍率。
- 使用中クエスト数。
- 検証状態。

### 6.2 編集

- 順序付き最大パーティー人数分のスロット。
- 敵マスター選択。
- 出場/控えのプレビュー。実際の境界は選択した試合ルールで決まる。
- グループ共通AIとレベル。
- スロット別AIとレベル。
- 能力倍率。
- 説明、表示順、UI選択可否、状態。

ドラッグ&ドロップを使う場合も、キーボードまたは上下ボタンで順序変更できるようにする。

同じ敵マスターを複数スロットへ入れることは許可する。試合用個体はスロット別に生成する。

### 6.3 派生表示

- 出場/控え別のHP・主要能力合計。
- AI役割の分布。
- 回復役、得点役、奪取役、守備役の有無。
- 使用スキル一覧。
- 各試合ルールへ適用した場合の人数適合状況。
- 参照中クエスト。

### 6.4 検証

- 空グループ不可。
- 無効または存在しない敵ID不可。
- 倍率が許容範囲内。
- AIプロフィールとレベルが有効。
- スロット間で戦闘用IDが一意に生成できる。
- 公開クエストで使う場合、そのルールの敵出場人数以上かつパーティー上限以下。

## 7. 参照関係と影響確認

管理対象は以下の依存グラフを持つ。

```text
Quest
  ├─ Field / Layout
  ├─ MatchRule
  ├─ EnemyGroup
  │    ├─ EnemyMaster
  │    │    ├─ Skill
  │    │    └─ default AIProfile
  │    ├─ group AIProfile
  │    └─ slot AIProfile
  ├─ Reward（存在する場合）
  └─ UnlockCondition（存在する場合）
```

編集画面から「どこで使われているか」を開けるようにする。

公開・無効化前には影響一覧を表示する。

- 直接参照する公開クエスト。
- 間接的に影響する敵グループ。
- 直近の試合利用件数。
- 変更で新しく発生するエラーと警告。

## 8. ログを4種類に分離する

### 8.1 運用・エラーログ

アプリの動作診断用。

主なイベント:

- 起動、終了、バージョン、環境。
- データロード開始/成功/失敗。
- 不正データ、フォールバック。
- 画面遷移失敗。
- 保存・読込失敗。
- 未処理例外。
- 外部サービス通信失敗。存在する場合。

レベル:

```text
DEBUG  開発時の詳細。入力座標や候補評価など
INFO   正常な重要イベント
WARN   継続可能な異常、フォールバック
ERROR  操作失敗、データ利用不能
FATAL  起動・主要処理を継続不能
```

毎フレームの通常状態や同じ警告を大量出力しない。繰り返しログには抑制、集約、一定時間ごとの再通知を使う。

### 8.2 戦闘イベントログ

プレイヤー表示、リプレイ調査、バグ解析の正となる構造化イベント。

必須共通項目:

```text
event_id: string
match_id: string
sequence: int
timestamp: datetime or elapsed time
event_type: string
round_or_turn: int
actor_instance_id: string?
target_instance_id: string?
source_action_id: string?
payload: object
schema_version: int
```

推奨イベント:

- match_started / match_finished。
- turn_started / turn_finished。
- action_selected / action_resolved。
- movement。
- damage / healing / resource_change。
- status_added / status_removed。
- object_transferred / object_dropped。
- score。
- knockout / revival。
- substitution。
- AI decision summary。開発・分析用途。

イベントは確定した結果から作る。ログのために乱数を振り直したり戦闘式を再実行しない。

### 8.3 試合集計レポート

一試合または複数試合を人間が分析するための派生データ。

一試合レポート:

1. 試合概要。
2. 試合条件。
3. 開始時参加者・敵マスター・AI。
4. 試合結果。
5. キャラクター別集計。
6. スキル別集計。
7. 行動イベント。
8. 試合全体集計。

複数試合集計:

- クエスト別試合数、勝率、平均ターン、平均得点。
- 敵グループ別勝率。
- 敵別の出場数、与被ダメージ、得点、戦闘不能、行動選択。
- スキル別使用率、成功率、実ダメージ、回復、過剰回復。
- リタイア率、エラー終了率。
- シードまたはビルドバージョン別比較。

### 8.4 管理監査ログ

管理データの変更履歴。通常のエラーログとは分離する。

```text
AuditEvent
  audit_id
  occurred_at
  actor_id                  ローカルなら "local_developer"
  action                    create/update/publish/disable/import/delete
  entity_type               quest/enemy/enemy_group/rule/field/ai
  entity_id
  version_before
  version_after
  before                    秘密情報を除いた変更前
  after                     秘密情報を除いた変更後
  changed_fields
  reason?
  correlation_id
```

監査ログは管理画面から編集・削除できない。ローカルファイル運用でも追記専用を基本とする。

## 9. ログ保存方針

### 9.1 実行環境と保存方針を分ける

```text
execution_mode:
  manual / auto / headless / editor_preview

output_policy:
  play / development / ci / test / none
```

実行方法がオートだから保存する、ヘッドレスだから保存しない、とは決めない。明示した保存方針で決める。

推奨:

- 通常プレイ: 構造化イベントまたは要約を保存。
- 開発: 詳細ログとレポートを保存。
- CI: 失敗調査に必要なログを成果物へ保存。
- 自動テスト: 原則メモリのみ。失敗時だけテスト基盤に表示。
- 管理プレビュー: プレイヤー履歴から分離して保存。

### 9.2 ファイル構成例

```text
logs/
  runtime/YYYY-MM-DD/app.jsonl
  matches/YYYY-MM-DD/{match_id}.jsonl
  reports/YYYY-MM-DD/{match_id}.md
  batches/YYYY-MM-DD/{batch_id}.json
  audit/YYYY-MM/audit.jsonl
```

DBを使う場合も論理区分を分ける。

### 9.3 安全な保存

- 文字コードUTF-8。
- JSON Linesまたは構造化DBを推奨。
- ファイル名へユーザー入力を直接使わない。
- `match_id` は衝突しないID。
- レポートファイルは一時ファイルへ書き、flush/close後に最終パスへ置換。
- 保存失敗はエラーログへ記録し、戦闘結果は可能な限り継続。
- 保存先を勝手に別環境へフォールバックしない。
- 大容量ログは日付またはサイズでローテーションする。

### 9.4 保持期間

設定可能にする。

- DEBUG実行ログ: 短期。
- エラーログ: 中期。
- 個別戦闘イベント: 容量に応じて短～中期。
- 集計結果: 長期。
- 監査ログ: 最長。運用要件に従う。

削除ジョブは対象カテゴリ、期間、件数、削除結果を監査または運用ログへ記録する。

### 9.5 秘密情報と個人情報

- APIキー、アクセストークン、パスワード、Cookieを記録しない。
- セーブ全体やHTTPヘッダーを無差別に記録しない。
- プレイヤー名、メール、IP等は必要性を確認し、マスクまたは匿名ID化する。
- 管理画面のbefore/afterへ秘密フィールドを含めない。
- ログコピー、ダウンロードにも同じマスク処理を適用する。

## 10. ログ管理画面

### 10.1 共通一覧

検索条件:

- 期間。
- ログ種別。
- レベル。
- クエストID。
- 試合ID。
- 敵グループID、敵マスターID。
- イベント種別。
- 実行モード、保存方針、環境、ビルドバージョン。
- 成功/警告/失敗。
- フリーテキスト。可能な範囲。

一覧列:

- 時刻。
- 種別/レベル。
- 環境。
- 要約。
- クエスト/試合ID。
- 相関ID。
- 詳細を開く操作。

大量データを全件メモリへ読み込まない。ページングまたは仮想スクロールを使用する。

### 10.2 試合一覧

- 開始・終了時刻。
- クエスト名/ID。
- モード、シード、ビルド。
- 味方/敵編成。
- 勝敗、終了理由、得点、ターン。
- 警告・エラー有無。
- レポート有無。

### 10.3 試合詳細

タブ例:

- 概要。
- 参加者。
- タイムライン。
- キャラクター集計。
- スキル集計。
- AI判断。開発モードのみ。
- 生イベントJSON。開発者のみ。

タイムラインは `sequence` 順を正とする。同一時刻でも順序が入れ替わらないようにする。

イベント詳細では、変更前後をすべて表示するのではなく、通常表示は差分を中心にする。必要時だけ完全スナップショットを展開する。

### 10.4 試合中の全ログ

- 試合開始から現在までのプレイヤー向け文章ログを時系列表示。
- スクロール、閉じる、全文コピー。
- モーダル表示中は背面入力とAI進行を停止。
- 閉じると同じ戦闘状態から再開。
- コピー失敗時は試合を止めず、画面メッセージを出す。
- 常設ログ欄を置くかはUI方針による。Mana's Ball は画面領域確保のためモーダルのみ。

### 10.5 エクスポート

- 表示中のログをJSONL、CSVまたはMarkdownで出力。
- 個別試合の完全レポートを出力。
- 検索結果を出す場合は件数上限と警告を設ける。
- ファイル出力前に機密情報をマスク。
- ブラウザではダウンロード、ローカルゲームでは保存先選択または規定フォルダ。

## 11. 構造化イベントの例

```json
{
  "schema_version": 1,
  "event_id": "evt_000124",
  "match_id": "match_20260808_ab12",
  "sequence": 124,
  "event_type": "action_resolved",
  "turn": 9,
  "actor_instance_id": "enemy:castle_guard:2",
  "target_instance_id": "player:1",
  "payload": {
    "action_id": "push_strike",
    "success": true,
    "calculated_damage": 8,
    "effective_damage": 5,
    "overkill_damage": 3,
    "position_before": [8, 2],
    "position_after": [8, 2],
    "target_hp_before": 5,
    "target_hp_after": 0,

```

ログスキーマを変更する場合は `schema_version` を上げ、読み取り側で旧版を扱うか、明示的な移行処理を用意する。

## 12. 実装構成

```text
AdminRouter / AdminScreen
  管理画面の遷移と権限確認

QuestAdminService
  クエスト下書き、検証、公開、複製

EnemyAdminService
  敵マスターと敵グループの管理

ReferenceGraphService
  参照元・参照先、変更影響を算出

GameDataValidator
  単体検証と全体統合検証

PreviewMatchService
  下書きデータを永続公開せずテスト実行

RuntimeLogger
  運用・エラーログ

BattleEventCollector
  確定済み戦闘イベントを順序付き収集

MatchReportBuilder
  イベントから集計と人間向けレポートを生成

AuditLogger
  管理変更履歴を追記

LogRepository / LogQueryService
  保存、検索、ページング、保持期間
```

重要な境界:

- 管理フォームは直接ゲーム中オブジェクトを変更しない。
- 公開リポジトリと下書きリポジトリを論理的に分ける。
- 戦闘ロジックはロガーの保存成功に依存しない。
- レポート生成は戦闘の正ではなく、確定イベントから作る派生処理。
- 監査ログは通常のアプリログや戦闘イベントと混ぜない。

## 13. 受け入れテスト

### 13.1 クエスト管理

1. 一覧検索、絞り込み、並び替え、ページングが動く。
2. 新規下書きを作成でき、ID重複を拒否する。
3. 既存クエストを別IDへ複製できる。
4. 存在しないフィールド、ルール、敵グループを検出する。
5. 人数、初期配置、初期保持者、ルール固有値を検証する。
6. エラーありの下書きを公開できない。
7. 警告だけなら確認後に公開できる。
8. 公開後、プレイヤー向けクエスト選択に一度だけ表示される。
9. 無効化後、新規のクエスト選択には表示されない。
10. 参照中データの危険な無効化を拒否する。

### 13.2 敵管理

1. 敵マスターを作成、複製、編集できる。
2. 能力、AIレベル、スキル参照を検証する。
3. 画像欠損時の警告とフォールバックが機能する。
4. 敵グループの順序を変更・保存できる。
5. 同じ敵を複数スロットへ登録できる。
6. 同一マスター由来の戦闘個体は状態が独立する。
7. グループ人数と各クエストの試合ルールの適合を表示する。
8. 敵・グループ編集時に参照中クエストを確認できる。

### 13.3 ログ

1. ログレベル、種別、期間、クエスト、試合、敵で検索できる。
2. ページングしても欠落や重複がない。
3. 戦闘イベントの `sequence` が一意かつ単調増加する。
4. UIログとレポートが同じ確定結果を表示する。
5. ログ生成による乱数消費や戦闘状態変更がない。
6. ログ保存失敗でも試合結果処理が継続する。
7. テスト方針では意図しないファイルが生成されない。
8. 一時ファイルからのレポート置換が成功し、同名衝突しない。
9. 全ログモーダル中は入力とAIが停止し、閉じると再開する。
10. コピー・エクスポート時に秘密情報が含まれない。
11. 管理変更ごとに監査イベントが一件記録される。
12. 監査ログを管理UIから変更・削除できない。
13. ローテーションと保持期間削除が対象外ログを消さない。
14. 旧 `schema_version` のイベントを仕様通り読めるか、明確な非対応表示になる。

### 13.4 統合確認

1. 管理画面で敵を作る。
2. その敵を含む敵グループを作る。
3. グループを参照するクエストを作る。
4. 全体検証する。
5. プレビュー戦闘を完走する。
6. 公開する。
7. プレイヤー向けクエスト選択に表示される。
8. 編成して試合を完走する。
9. 試合ログと集計レポートを管理画面で確認する。
10. 一連の管理操作を監査ログで追跡できる。

## 14. 実装優先順位

### 第1段階: 最小構成

- クエスト・敵・敵グループの読み取り専用一覧と詳細。
- 全データ検証画面。
- 戦闘イベント収集。
- 個別試合ログ閲覧。

### 第2段階: ローカル編集

- 下書き作成、編集、複製。
- 原子的なファイル保存。
- プレビュー戦闘。
- 公開/無効化。
- 変更履歴。

### 第3段階: 分析

- 複数試合の集計。
- クエスト・敵・スキル別比較。
- バッチシミュレーション。
- CSV/JSON/Markdownエクスポート。

### 第4段階: 複数ユーザー運用が必要な場合

- 認証、権限。
- 楽観ロック。
- DB永続化。
- 監査ログ保護。
- バックアップと復元。

ローカル単独開発しか行わないゲームへ、最初から第4段階の構成を入れる必要はない。

## 16. 注意事項

- 管理画面は本番プレイヤーから到達できないようにする。
- ローカルゲームであっても、破損した公開データへ直接上書きしない。
- CSV、JSON、DBのどれを使っても、参照整合性と公開前検証を省略しない。
- ログ本文だけに情報を残さず、検索したい項目は構造化フィールドへ格納する。
- 大きなbefore/afterスナップショットを全イベントへ無制限に複製しない。差分と必要な確定値を中心にする。
- ログ画面のために全ログを一括ロードしない。
- DEBUGログを通常プレイで常時有効にしない。
- エラーを握りつぶさず、プレイヤー継続可否と開発者向け原因の両方を残す。
- ログをゲーム状態の正として扱うリプレイを将来実装する場合は、イベント決定性、スキーマ互換、初期スナップショットを別途厳密に設計する。
