# Direct Implementation

個別仕様書を別のCodex用実装指示書へ変換せず、その内容を従来の「13．今回の仕様本文」として直接使用し、調査だけで終了せず実装から確認、修正、報告まで完遂する。

## 1．適用と仕様入力元

このSkillが指定された場合、次の優先順位で今回の仕様本文を決定する。

1. 現在のユーザー依頼に直接記載された個別指示。
2. 現在のユーザー依頼へ直接貼り付けられた仕様書。
3. 現在のユーザー依頼で明示された仕様ファイル。
4. `docs/implementation/current.md`。
5. `AGENTS.md`。
6. READMEおよび既存仕様書。

直接貼り付けられた仕様書または選択した仕様ファイルの内容全体を「13．今回の仕様本文」として扱う。見出しの追加、並べ替え、要約、実装指示書への再編集は行わない。見出しが一部不足していても実装可能な内容があれば使用する。

`$direct-implementation`だけが指定され、貼り付け本文もファイル指定もない場合は、`docs/implementation/current.md`を使用する。ファイルが存在しない、空である、または「ここに今回の実装目的を記載する。」などの記入例だけである場合は有効な仕様とみなさず、対象コードやデータを変更せず、実装可能な仕様がないことを報告する。

## 2．最初に確認する内容

作業開始時に、プロジェクト直下から対象ファイルまでの適用範囲にある`AGENTS.md`、`AGENTS.override.md`、READMEを確認する。プロジェクト固有の実装方針、変更・調査範囲、実行環境、コード・データ・アセット・ログ規則、テスト方法、Gitと外部操作の禁止事項、完了条件、最終報告形式に従う。今回のユーザー依頼に明確な個別指示がある場合は、その指示を優先する。

`AGENTS.md`はプロジェクト固有規則、このSkillは直接実装の作業手順、`current.md`は今回の個別仕様を管理する。同じ共通規則を`current.md`へ複製しない。

## 3．調査

調査中はコードを変更しない。仕様本文に含まれる画面名、機能名、状態名、データ項目、表示文言を検索し、次の順序を基本に対象を絞る。

1. 適用範囲の指示ファイルとREADME、仕様・設計文書。
2. 主要構成と起動ファイル。
3. 対象画面またはシーン。
4. 入力、更新、描画、状態管理の処理。
5. 関係するCSV、JSON、設定、画像、フォント、アセット。
6. ログ方式、既存テスト、起動方法。

最初から全ファイルを無条件に読まない。初回確認は原則3～8ファイル程度とし、正しい実装に必要な関連ファイルだけ追加確認する。調査後、現在の処理経路、接続箇所、再利用対象、変更・追加ファイル、データ変更、影響範囲、実装手順、テスト方法、起動後の確認方法を内部的に整理し、停止条件に該当しなければ回答を待たず実装へ進む。

## 4．実装停止条件

不明点は既存実装と仕様から合理的に仮決めし、完了報告へ記載する。ただし、次の場合は変更を停止し「要確認」として報告する。

* 既存ファイルやデータの大量削除が必要。
* セーブデータや既存データの互換性を大きく失う。
* 主要システム全体の作り直しが必要。
* 実装方法で結果が大きく異なり、後から戻すことが困難。
* 外部サービスへの接続、公開、課金が必要。
* APIキー、パスワード、認証情報が必要。
* ユーザーの既存変更を破棄する必要がある。
* 本番環境への変更が必要。

## 5．直接実装

既存の命名と処理を再利用し、今回の仕様に関係する最小差分で実装する。仕様中の仮のファイル名、クラス名、関数名を無条件に新設せず、役割と接続先から既存プロジェクト内の適切な箇所を特定する。必要に応じ、データ定義、定数・設定値、状態管理、内部判定、入力、描画、画面遷移、エラー処理、必要最小限のログの順に接続する。

重複実装、不要な新規ファイル、無関係なリファクタリング、過剰なUIや演出、仕様の大幅拡張を避ける。調整値は既存方式に合わせ、旧データには可能な限り既定値で対応する。一時デバッグコードと毎フレーム大量に出るログを残さない。既存のユーザー変更を維持する。

## 6．静的確認

ゲーム起動前に、言語の構文、import、未定義名、呼び出し引数、戻り値、ファイルパス、CSV列、JSONキー、画像・フォントパス、循環import、旧データ互換性を確認する。無関係な差分、一時ファイル、デバッグコードがないことも確認し、関係する既存テストを実行する。新規テストは対象機能の確認に必要な最小限だけ追加する。

## 7．テスト、ゲーム起動、ログ確認

`AGENTS.md`、README、既存スクリプト、起動ファイルに従い、既存環境でゲームを起動する。新しい仮想環境を作らず、指示されていないライブラリを追加・更新しない。GUIが終了待ちになる場合は時間を区切り、標準出力、標準エラー、ログ、例外を確認する。

可能な範囲で、起動、初期画面、対象画面への接続、入力反映、状態更新、描画用情報、既存データとアセットの読込、主要既存機能、未処理例外の有無を確認する。GUIを自動操作できなければ、対象画面の生成、関数呼出し、状態と描画データの更新、ログを確認し、人間による確認事項を報告する。

## 8．エラー修正

エラー時はメッセージとスタックトレースを確認し、今回の変更か既存不具合かを切り分ける。原因ファイル、関数、データを特定し、変更範囲内の最小差分で修正して同じ確認を再実行する。対象機能と既存機能への影響を再確認する。無関係な既存不具合は大規模修正せず未対応事項として報告する。

## 9．最終レビュー

個別仕様の実装漏れ、初回実装範囲、後回し範囲の誤実装、不要・無関係な変更、デバッグコード、不要ログ、一時ファイル、既存機能への影響、仮決め、未確認事項を差分から確認する。問題があれば報告前に修正する。

Git push、force push、既存変更を破棄するGit操作、本番デプロイ、外部公開、秘密情報の表示は、明示的な許可と必要性がない限り行わない。

## 10．完了報告

最終報告は簡潔に、次の見出しと内容で行う。

### 調査結果

* 確認した主要ファイル。
* 対象処理の現在の流れ。
* 既存処理との接続箇所。
* 採用した実装方針。

### 変更したファイル

ファイルごとに、ファイル名、変更内容、変更理由、既存処理との接続点を記載する。

### 追加したファイル

ファイルごとに、ファイル名、役割、追加理由を記載する。追加がなければ「なし」とする。

### 実装内容

実装した機能を項目別に記載する。

### 動作確認結果

実行コマンド、テスト、確認操作、結果、発生したエラー、修正内容を記載する。

### 仮決め事項

仮決めした内容と理由を記載する。なければ「なし」とする。

### 未確認事項

環境や画面操作の都合で確認できなかった内容を記載する。なければ「なし」とする。

### 人間が確認する内容

ゲーム画面で最終確認が必要な操作と期待結果を記載する。なければ「なし」とする。
